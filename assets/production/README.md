## Local candidate review

For future batches, put candidate GLBs in `assets/candidates/runtime/` and a candidate manifest in `assets/candidates/manifest.json`. It uses the regular asset fields, `acceptance: pending-approval`, and paths such as `/__asset-review/runtime/hero.glb`. Start the local Vite dev server and open `/rehearse?reviewAssets=1` on localhost. The source manifest remains unapproved while this view loads candidate art.

The candidate middleware is development-only, binds review to loopback requests, rejects path/symlink escapes and malformed/external-resource GLBs before serving, and does not copy candidates into the production public directory. The review page displays a candidate banner. No asset is automatically approved by loading it. Capture the actual Babylon view and record socket/collider/silhouette/material checks before admitting a final GLB.

Static inspection in `scripts/lib/glb.mjs` supports the initial kit's embedded core triangle geometry, rigid TRS animations, PNG/JPEG and unlit/texture-transform extensions. Skinning, morphs, sparse/matrix accessors, external resources, compressed streams and other extensions are explicitly rejected. Export core glTF metallic/roughness materials and rigid transform animation from Blender; inspect failures before changing policy. Bounds cover the selected scene's rest pose and do not establish animation-envelope or GPU acceptance.

`npm run test:assets` runs dependency-free authored fixture checks with Node24. These lightweight checks do not install packages or run the game/provider suites. Candidate and Blender source assets are excluded from the Docker build context. The audit stage receives approved concept/capture evidence, while the final service image copies only runtime code/dependencies and the built web bundle. Only an admitted GLB with local provenance/concept/capture records, measured scene triangles, required sockets/animations and valid dimensions can pass `check-assets` as approved.
